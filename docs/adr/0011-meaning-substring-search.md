# ADR-0011：搜释义改用注释子串检索

- 日期：2026-11-21
- 状态：已接受（2026-11-21 实施；随 0.5-alpha.6 发布待定）

## 背景

「搜释义」原实现把用户输入直接交给 FTS5：

```sql
SELECT 字組, 語言, 讀音, 註釋, 排序 FROM langs WHERE 註釋 MATCH ? ORDER BY 排序 LIMIT 200
```

`langs` 是 FTS5 虚表，默认 `unicode61` 分词器把**连续汉字视为一个 token**，`MATCH` 只有在
整个 token 等于查询词时才命中——用户搜「东西」只能找到注释恰好写作「东西」的 256 行，而注释里
真正含「东西」子串的有 916 行。常见的省略写法「~东西:找东西」（`~` 代指本条字组）更是完全搜不到：
使用者案例 `尋|岳陽路口|dʑin2|~东西:找东西` 在旧实现下搜「东西」无结果。旧实现还有 `LIMIT 200`，
命中一多就把排序靠后的条目挤掉。

量测（`siongdict.db`，只读 sqlite3，2026-11-21）：

| 查询方式 | 命中行数 | 说明 |
| --- | --- | --- |
| `註釋 MATCH '东西'` | 256 | 只命中 token 恰为「东西」的注释 |
| `註釋 MATCH '东*'` | 377 | 前缀 MATCH 只能匹配 token 开头 |
| `註釋 MATCH '东'` | 42 | 单字 token，漏掉「东西」等复合词 |
| `註釋 LIKE '%东西%'` | 916 | 与 instr 同值，但 LIKE 要额外转义 `%`／`_` |
| `instr(註釋,'东西') > 0` | 916 | 子串真值 |
| `instr(註釋,'东') > 0` | 1,007 | 单字子串 |
| 注釋含 `~` | 144,977 | 占全库 609,323 行的 23.8% |
| 注釋含 `~` 且 `字組` 含空格 | 92 | 两写法并列（如 `□ 櫟`），`~` 还原属近似 |

## 决策

1. **子串匹配**：用 `instr(註釋, ?) > 0` 做真子串检索，不再依赖 FTS5 分词：

   ```sql
   (instr(註釋, ?) > 0
     OR (instr(註釋, '~') > 0
         AND instr(REPLACE(註釋, '~', substr(字組, 1, instr(字組 || ' ', ' ') - 1)), ?) > 0))
   ```

   第二支先把注释里的 `~` 还原成该条字组的本字（取 `字組` 第一个空白分段），再对还原后的文本做子串匹配。
2. **字形变体**：`variants.expand(input)` 展开繁简／异体，按「与原输入不同的字数」升幂排序，取前 4 组
   （`MAX_MEANING_EXPANSIONS = 4`）；每个变体绑定上述条件的两个占位符，多组用 `OR` 连接。
3. **上限与排序**：`LIMIT 2000`（`MEANING_LIMIT`），仍 `ORDER BY 排序`（音典排序）。输入去掉首尾空白后为空则直接返回空表。
4. **端口不变**：`Lexicon.searchByMeaning(keyword)` 签名与返回类型不变，上层（`SearchViewModel`、结果卡片）无改动。

## 否决的方案

- **`LIKE '%…%'`／`GLOB`**：`LIKE` 要把查询里的 `%`、`_` 转义，`GLOB` 还会解释 `*`、`?`、`[]`，
  用户输入的 IPA／方括号注释会误伤；语义与 `instr` 相同但更易出错。
- **FTS5 `trigram` 分词器**：子串检索的正确解法，但要重建 FTS 表（`siongdict.db` 每次上游更新整体重建），
  且 `trigram` 对单字／双字查询支持有限，资料管线与体积代价都不小。留作将来若子串检索变慢时的选项。
- **启动时把全量注释读进内存做索引**：609,323 行注释全量驻留会增加启动时间与内存峰值，而查询本身在装置上
  是百毫秒级（见「后果」），不值得。
- **前缀 `MATCH '东*'`**：只能匹配 token 开头，搜「东西」时「~东西:找东西」这类注释仍搜不到（`~` 不是 token 边界）。
- **整词 MATCH 失败后用 `LIKE` 兜底**：等于把全表扫两遍，查询时间翻倍，结果还要合并去重。

## 后果

- **每次查询全表扫描 609,323 行**（4 个变体最多扫 4 遍）。桌面 sqlite3 实测：单模式 111 ms、含 `~` 还原的完整
  SELECT 197 ms、4 个变体约 0.53 s。**2026-11-21 装置实测**（模拟器 API 35，`DataLayerTest.meaningSearchMatchesSubstringsAndExpandsTilde`）：
  搜「寻东西」四变体 **514 ms / 5 行**；搜「东」两变体 **294 ms / 1,278 行**（均为单次采样，复跑落在
  455–514 ms / 286–341 ms，有浮动）。远低于 2 s 的决策阈值，故
  `MAX_MEANING_EXPANSIONS` 维持 4。
- 常见单字命中极多（「子」在注释中出现 12,445 行），结果截前 2,000 条，按音典排序而非相关度——这是「反查读音」
  工具可接受的取舍；真要分页再单独设计。
- 对**单 token 查询**，新结果是旧结果的**超集**：旧 `MATCH` 能命中的一定也能被子串命中，既有单字查询不会变少；
  多 token／短语查询的 FTS5 语义（AND 组配）与子串语义本就不同，不适用超集关系。
- `~` 还原取 `字組` 第一个空白分段：144,977 行里只有 92 行是多字组（两写法并列，首段可能是 `□` 占位），
  对这 92 行属近似还原；其余 144,885 行第一个分段就是本字。
- 少了 FTS5 的索引加速，换来的是「不再漏结果」与「注释省略号可搜」，这是本 ADR 的核心取舍。

## 实测（2026-11-21，只读 sqlite3）

- 全库 609,323 行；使用者案例 `尋|岳陽路口|dʑin2|~东西:找东西` 存在（同注释还见于 `常寧官嶺`、`常德前河`）。
- 子串：`instr(註釋,'东西') > 0` = 916 行；`instr(註釋,'东') > 0` = 1,007 行；把 `~` 还原成字组本字后，
  注释含「尋」的 = 30 行（原文直接含「尋」只有 6 行、含「寻」46 行、两者任一 52 行）；用户查询
  「寻东西」的四个字形变体合并后命中 5 行。
- 装置实测（2026-11-21，模拟器 API 35，仪器化 logcat）：`meaningSearch rows=5 elapsedMs=514 dongRows=1278 dongMs=294`
  —— 搜「寻东西」命中 5 行（与桌面 sqlite3 的 5 行一致）、耗时 514 ms；搜「东」命中 1,278 行、294 ms。
